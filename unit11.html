Protocol-Layer Security

The same building blocks (symmetric encryption, MACs, Diffie–Hellman, certificates) can be placed at different layers of the TCP/IP stack. Chapter 17 places them just above TCP: TLS, HTTPS built on it, and SSH. Chapter 20 places them in IP itself: IPsec protects every packet a host or gateway sends, with ESP doing the work, security associations and policy databases deciding what to do with each packet, and IKEv2 setting up the keys.

17.1Web Security Considerations

The Web is a client/server application over the Internet and TCP/IP intranets, so earlier tools apply. A few features of Web use make tailored tools necessary.

  • Browsers are easy to use, servers easy to configure and content easy to develop, but the underlying software is extraordinarily complex and may hide many security flaws.
  • A subverted Web server can be a launching pad into the organization’s entire computer complex: data and systems connected to the server at the local site.
  • Casual, untrained users are common clients; they may not know the risks or have the tools to counter them.

Web security threats

Passive attack — eavesdropping on traffic between browser and server, or gaining access to restricted information on a Web site. Active attack — impersonating another user, altering messages in transit, or altering information on a Web site.

Threats can also be classed by location: Web server, Web browser, or network traffic between them. Server and browser security are computer system security; traffic security is network security, the subject of this chapter.

17.2Transport Layer Security

TLS is a general-purpose service built as a set of protocols on TCP. The book describes version 1.2 (RFC 5246).

Transport Layer Security (TLS) — an Internet standard that evolved from the commercial Secure Sockets Layer (SSL); SSL is deprecated by the IETF. TLS uses TCP to provide a reliable end-to-end secure service. It can be part of the underlying protocol suite (transparent to applications) or embedded in specific packages such as browsers and Web servers.
CorrectionThe book abbreviates Transport Layer Security as “TSL” once; the abbreviation is TLS. Version 1.3 has since been published as RFC 8446 (the book describes a draft).

TLS architecture

TLS is two layers of protocols. The Record Protocol gives basic security services to higher-layer protocols, including HTTP. Three TLS-specific higher-layer protocols manage TLS exchanges: Handshake, Change Cipher Spec and Alert. A fourth, the Heartbeat protocol, is defined in a separate RFC.

Redrawn from Figure 17.2, TLS protocol stack.
TLS connection — a transport (OSI definition) giving a suitable type of service; a transient, peer-to-peer relationship. Every connection is associated with one session.
TLS session — an association between a client and a server, created by the Handshake Protocol. It defines a set of cryptographic security parameters that several connections can share, avoiding expensive renegotiation for each connection.

Between a pair of parties there may be many secure connections; multiple simultaneous sessions are possible in theory but not used in practice. Each session has a current operating state for read (receive) and write (send). During the Handshake Protocol, pending read and write states are created; on success they become the current states.

Session state

Session identifier: arbitrary bytes chosen by the server to identify an active or resumable session. Peer certificate: the peer’s X.509v3 certificate (may be null). Compression method: algorithm applied before encryption. Cipher spec: bulk encryption algorithm (null, AES…) and hash for MAC calculation (MD5, SHA-1), with attributes such as hash_size. Master secret: 48-byte secret shared by client and server. Is resumable: whether the session can start new connections.

Connection state

Server and client random: bytes chosen by each side for each connection. Server / client write MAC secret: key for MAC operations on data sent by the server / client. Server / client write key: symmetric encryption key for data the server / client encrypts. Initialization vectors: one per key for CBC; first set by the Handshake, then the last ciphertext block of each record is the IV for the next. Sequence numbers: separate send and receive counters, reset to zero on a change cipher spec message, at most 264 − 1.

Initialization vector (IV) — the starting block that CBC mode (Unit 5) XORs into the first plaintext block, so equal plaintexts encrypt differently.

TLS Record Protocol, Change Cipher Spec and Alert

The Record Protocol is the workhorse: every byte TLS carries, including its own control messages, travels inside a record.

The Record Protocol gives TLS connections two services, both using keys the Handshake Protocol defines: confidentiality (conventional encryption of payloads) and message integrity (a MAC). It fragments application data, optionally compresses, adds a MAC, encrypts, adds a header and sends the result in a TCP segment. Received data are decrypted, verified, decompressed and reassembled.

  1. Fragment into blocks of 214 = 16,384 bytes or less.
  2. Compress (optional): lossless, may not grow the content by more than 1024 bytes. No algorithm is specified in TLS 1.2, so the default is null.
  3. Add MAC with HMAC (Unit 7): HMAC_hash(MAC_write_secret, seq_num ‖ TLSCompressed.type ‖ TLSCompressed.version ‖ TLSCompressed.length ‖ TLSCompressed.fragment).
  4. Encrypt the compressed message plus MAC: AES (128 or 256-bit key) or 3DES (168) as block ciphers, RC4-128 as a stream cipher. Encryption may not add more than 1024 bytes, so the total stays within 214 + 2048. For block ciphers, padding bytes plus a one-byte padding length go after the MAC; the padding can be any amount making the total a multiple of the block length, up to 255 bytes. Variable padding frustrates attacks based on message lengths.
  5. Append the header: Content Type (8 bits), Major Version (8), Minor Version (8), Compressed Length (16 bits, at most 214 + 2048).
HMACK(M) = H[(K+ ⊕ opad) ‖ H[(K+ ⊕ ipad) ‖ M]]ipad = 0x36 × 64, opad = 0x5C × 64

Content types: change_cipher_spec, alert, handshake (the TLS-specific protocols) and application_data. TLS makes no distinction among applications; their data are opaque to it.

CorrectionThe book gives the header version as 3 / 1 “for TLSv2”. There is no TLS 2; 3.1 is the wire value of TLS 1.0, and TLS 1.2 is 3.3 (RFC 5246, Appendix E).

Change Cipher Spec Protocol

The simplest of the four protocols that use the Record Protocol: a single message of one byte with value 1. Its only purpose is to copy the pending state into the current state, updating the cipher suite used on this connection.

Alert Protocol

Conveys TLS-related alerts to the peer. Alert messages are compressed and encrypted like any other data under the current state. Each is two bytes: a level (warning 1 or fatal 2) and an alert code. A fatal alert terminates the connection immediately; other connections on the session may continue, but no new connections may be established on it.

Handshake Protocol

The most complex part of TLS. Before any application data, client and server authenticate each other and agree an encryption algorithm, a MAC algorithm and the keys that will protect records.

Every handshake message has three fields: Type (1 byte, one of 10 messages), Length (3 bytes), Content (≥ 0 bytes, the parameters).

Phase 1 · Establish security capabilities

The client sends client_hello:

  • Version: highest TLS version the client understands.
  • Random: 32-bit timestamp plus 28 bytes from a secure random number generator. These are nonces (values used once), used in key exchange to prevent replay attacks.
  • Session ID: nonzero to update an existing connection’s parameters or open a new connection on this session; zero for a new connection on a new session.
  • CipherSuite: the combinations of algorithms the client supports, most preferred first. Each defines a key exchange algorithm and a CipherSpec.
  • Compression Method: compression methods the client supports.

The server_hello carries the same parameters: Version is the lower of the client’s suggestion and the server’s highest; Random is generated independently; Session ID repeats a nonzero client value or names a new session; CipherSuite and Compression are the single choices the server picked from the client’s lists.

Key exchange methods

RSA

The secret key is encrypted with the receiver’s RSA public key; a public-key certificate for that key must be available.

Fixed Diffie–Hellman

The server’s certificate contains its Diffie–Hellman public parameters, signed by the CA. The client’s DH parameters come in a certificate or a key exchange message. Produces a fixed secret key between the two peers.

Ephemeral Diffie–Hellman

Temporary, one-time keys. The DH public keys are exchanged signed with the sender’s private RSA or DSS key, and certificates authenticate the public keys. The most secure of the three DH options: a temporary, authenticated key.

Anonymous Diffie–Hellman

Base DH with no authentication: each side sends its public parameters unsigned. Vulnerable to a man-in-the-middle who runs anonymous DH with both parties.

Diffie–Hellman key exchange (Unit 6) — each side picks a private random number, sends g raised to it mod p, and both compute the same shared secret; an eavesdropper would have to solve a discrete logarithm. Man-in-the-middle attack — an attacker relays between two parties while running a separate exchange with each, so both unknowingly share keys with the attacker.

A CipherSpec follows the key exchange method: CipherAlgorithm (RC4, RC2, DES, 3DES, DES40, IDEA), MACAlgorithm (MD5 or SHA-1), CipherType (stream or block), IsExportable, HashSize (0, 16 or 20 bytes), Key Material (data used to generate the write keys) and IV Size.

Phase 2 · Server authentication and key exchange

The server sends its certificate (one or a chain of X.509 certificates) for every method except anonymous DH; with fixed DH this message doubles as the server’s key exchange. A server_key_exchange follows unless the server sent fixed DH parameters or RSA key exchange is used. It carries: for anonymous DH, the prime, the primitive root and the server’s DH public key; for ephemeral DH, the same plus a signature; for RSA with a signature-only key, a temporary RSA public key (exponent, modulus) plus a signature.

signature covers hash(ClientHello.random ‖ ServerHello.random ‖ ServerParams)

Including both nonces guards against replay and misrepresentation. DSS signs a SHA-1 hash; RSA encrypts the 36-byte concatenation of an MD5 and a SHA-1 hash with the server’s private key. A non-anonymous server may then send certificate_request (certificate_type: RSA or DSS signature-only, or RSA/DSS for fixed DH; and a list of acceptable CAs). Phase 2 always ends with server_done, which has no parameters.

Phase 3 · Client authentication and key exchange

The client checks the server certificate and hello parameters. If a certificate was requested it sends one (or a no_certificate alert). The client_key_exchange is mandatory: for RSA, a 48-byte pre-master secret encrypted with the server’s public key; for ephemeral or anonymous DH, the client’s DH public parameters; for fixed DH, null (the parameters were in the certificate). A certificate_verify may follow any client certificate with signing capability: a signature over a hash of all handshake messages so far, proving the client owns the certificate’s private key.

Phase 4 · Finish

The client sends change_cipher_spec (Change Cipher Spec Protocol, not part of the Handshake), copies the pending CipherSpec into the current one, then sends finished under the new algorithms and keys. The server does the same. Then application data can flow.

finished = PRF(master_secret, finished_label, MD5(handshake_messages) ‖ SHA-1(handshake_messages)) finished_label = “client finished” or “server finished”

Cryptographic Computations

The key exchange only produces one shared value. Everything the Record Protocol needs is stretched from it by a pseudorandom function.

Master secret creation

The master secret is a one-time 48-byte (384-bit) value for the session, made in two stages. First a pre_master_secret is exchanged: with RSA, the client generates 48 bytes, encrypts them with the server’s public RSA key and the server decrypts; with Diffie–Hellman, both sides compute it from the exchanged public keys. Then both compute:

master_secret = PRF(pre_master_secret, “master secret”, ClientHello.random ‖ ServerHello.random) key_block = PRF(master_secret, “key expansion”, server_random ‖ client_random)

The key block is cut, in order, into the client write MAC secret, server write MAC secret, client write key, server write key, client write IV and server write IV. The master secret acts as the pseudorandom seed; the two random values act as salt (public values mixed in to complicate cryptanalysis).

Pseudorandom function (PRF) — expands a small shared secret into longer blocks of data for key generation or validation, in a way secure against attacks on hash functions and MACs.
P_hash(secret, seed) = HMAC_hash(secret, A(1) ‖ seed) ‖ HMAC_hash(secret, A(2) ‖ seed) ‖ … A(0) = seed, A(i) = HMAC_hash(secret, A(i − 1)) PRF(secret, label, seed) = P_<hash>(secret, label ‖ seed)

P_hash is iterated until enough output exists; each iteration runs HMAC twice (once for A(i), once for the output block). The book also shows an older key_block formula of the form MD5(master_secret ‖ SHA(“A” ‖ master_secret ‖ ServerHello.random ‖ ClientHello.random)) ‖ MD5(… “BB” …) ‖ …; that construction is the one SSL 3.0 used.

CorrectionThe book says P_MD5 needs four iterations to produce 80 bytes, “exactly 64 bytes”. Four 16-byte blocks give only 64 bytes; 80 bytes need five iterations. P_SHA256 (32-byte blocks) needs three, giving 96 bytes of which 16 are discarded, as the book says.

Heartbeat Protocol, TLS Attacks and TLSv1.3

Two TLS extras the book covers after the core: a keep-alive protocol, and the steady cycle of attacks and fixes that led to version 1.3.

Heartbeat — in computer networks, a periodic signal from hardware or software indicating normal operation or synchronizing other parts of a system. A heartbeat protocol typically monitors whether a protocol entity is available.

The TLS Heartbeat protocol (RFC 6520) runs over the Record Protocol with two messages, heartbeat_request and heartbeat_response. Support is agreed in Phase 1 of the handshake: each peer says whether it will receive requests and answer, or only send requests. A request may be sent at any time and must be answered promptly.

  • The request carries payload length, a payload (random, 16 bytes to 64 KB) and padding (random). The response must contain an exact copy of the payload.
  • Increasing padding until no answer comes back lets the sender discover the path MTU (maximum transfer unit).
  • Purposes: assure the sender the peer is still alive during idle periods, and generate activity so a firewall that dislikes idle connections does not close it.
  • The payload exists for DTLS (Datagram TLS, a connectionless version) where packets can be lost: it matches responses to requests. The same protocol is used with TLS for simplicity.
Lab · Heartbeat echoRFC 6520 §4

RFC 6520 requires at least 16 bytes of padding and requires a receiver to silently discard a request whose payload_length is too large for the record it arrived in. The book does not cover this length check.

SSL/TLS attack categories

Each new attack has forced changes to the protocol, the cryptographic tools or the implementation.

Handshake protocol

Exploiting the formatting and implementation of the RSA encryption scheme; refined as countermeasures appeared, both to defeat them and to speed up the attack.

Record and application data

BEAST (Browser Exploit Against SSL/TLS) used a chosen-plaintext attack: guessing the plaintext behind a known ciphertext. CRIME (Compression Ratio Info-leak Made Easy) recovers Web cookies when compression is used with TLS, enabling session hijacking of an authenticated session.

PKI

Checking X.509 certificate validity is attackable; widely used SSL/TLS libraries were shown to have vulnerable certificate validation.

Other

A denial-of-service attack that floods a server with handshake requests (new connections or renegotiation). The server does most handshake computation, so it carries more load than the attacker.

Chosen-plaintext attack (Unit 3) — the analyst gets plaintexts of its choosing encrypted and studies the results. Session hijacking — taking over an authenticated session by obtaining what identifies it, such as a session cookie.

TLSv1.3

The primary aim is better security. Significant changes from 1.2:

  • Removed, to cut the chance of coding errors and the attack surface: compression; ciphers without authenticated encryption; static RSA and DH key exchange; the 32-bit timestamp in client_hello Random; renegotiation; the Change Cipher Spec Protocol; RC4; MD5 and SHA-224 with signatures.
  • Key exchange only by DH or ECDH, never RSA. If an RSA private key is compromised, every handshake that used it is compromised; with DH or ECDH a new key is negotiated per handshake.
  • 1-RTT handshake: the client sends its key exchange parameters before a cipher suite is agreed, so the server can compute keys before its first response. Fewer packets: faster, smaller attack surface.
Authenticated encryption (Unit 7) — a single mode, such as GCM or CCM, that gives confidentiality and integrity together. Round-trip time (RTT) — one message out and its reply back.

17.3HTTPS

HTTPS is HTTP carried over SSL/TLS between browser and server (RFC 2818, HTTP Over TLS). Using HTTP over SSL or TLS makes no fundamental difference; both are HTTPS.

HTTPS (HTTP over SSL) — HTTP combined with SSL/TLS for secure browser–server communication. Built into all modern browsers; it needs a server that supports it. URLs begin https://; port 443 is used instead of HTTP’s port 80.
Lab · What an eavesdropper seesSection 17.3
encrypted by TLSvisible on the wire

With HTTPS the book lists as encrypted: the URL of the requested document, document contents, browser form contents, cookies in both directions and HTTP header contents. The IP addresses and TCP ports belong to lower layers and stay visible.

Connection initiation

The HTTP client is also the TLS client. It opens a connection to the server’s port, sends the TLS ClientHello, and after the handshake sends its first HTTP request; all HTTP data go as TLS application data. There are three levels of awareness of a connection:

  • HTTP level: the HTTP client asks the next lowest layer (normally TCP, but it may be TLS/SSL) for a connection to the HTTP server.
  • TLS level: a session is established between TLS client and server; it can support one or more connections at a time.
  • TCP level: a TLS connection request starts with a TCP connection between the TCP entities on each side.

Connection closure

An HTTP record containing Connection: close announces that the connection closes after that record. TLS must close its connection with the peer, which closes TCP. Each side should send a close_notify alert before closing; an implementation may close after sending its own without waiting for the peer’s (an incomplete close) and may then reuse the session, but only when the application knows it has received all the data it cares about. An HTTP client must also cope with TCP closing with no close_notify and no Connection: close; that could be an error or an attack, so the client should issue a security warning.

17.4Secure Shell (SSH)

SSH is a protocol for secure network communication designed to be simple and inexpensive to implement. It replaces remote logon schemes such as TELNET that offered no security, and also serves file transfer, email and X tunneling.

Secure Shell (SSH) — a client/server protocol for secure remote logon and general secure communication. SSH2 fixes security flaws in the original SSH1 and is documented in RFCs 4250–4256.
Forward secrecy — if a key is compromised during one session, that knowledge does not affect the security of earlier sessions.

Transport Layer Protocol

Server authentication, data confidentiality and integrity with forward secrecy; optional compression.

User Authentication Protocol

Authenticates the user to the server.

Connection Protocol

Multiplexes several logical channels over one SSH connection.

SSH Transport Layer Protocol

Server authentication happens here, before any user is authenticated, so the user never talks to an impostor.

Host keys

The server holds a public/private host key pair (possibly several, for different algorithms; several hosts may share one). The client must know the server’s public host key in advance. RFC 4251 allows two trust models:

Local database

The client associates each host name (as typed) with its public host key. No central infrastructure or third party, but the database can become burdensome to maintain.

Certification authority

A trusted CA certifies the name-to-key association; the client stores only the CA root key. Easier to maintain, but every host key must be certified before use.

Packet format

After the client opens a TCP connection, client and server exchange packets in the data field of TCP segments.

  • After the MAC is computed, the entire packet except the MAC is encrypted.

The packet length field is 4 bytes and padding length 1 byte (RFC 4253 §6). RFC 4253 also requires at least 4 bytes of padding, which the book does not mention; the lab applies it.

Packet exchange

  1. Identification string exchange: each side sends SSH-protoversion-softwareversion SP comments CR LF (e.g. SSH-2.0-billsSSH_3.6.3q3). These strings feed the key exchange hash.
  2. Algorithm negotiation: each side sends SSH_MSG_KEXINIT with preference-ordered lists for key exchange, encryption, MAC and compression. For each category the chosen algorithm is the first on the client’s list that the server also supports.
  3. Key exchange: one of two Diffie–Hellman versions (RFC 2409), one packet each way.
  4. End of key exchange: both send SSH_MSG_NEWKEYS; from now on keys derived from K are used.
  5. Service request: the client sends SSH_MSG_SERVICE_REQUEST for the User Authentication or Connection Protocol. All later data are SSH packet payloads protected by encryption and MAC.

Key exchange

C is the client, S the server; p a large safe prime; g a generator for a subgroup of GF(p); q the order of the subgroup; V_C, V_S the identification strings; K_S the server’s public host key; I_C, I_S the two SSH_MSG_KEXINIT messages. p, g, q and hash() come from algorithm negotiation.

Safe prime — a prime p of the form 2q + 1 with q also prime. Generator (Unit 4) — an element whose powers produce every element of a group or subgroup; here its powers mod p form the subgroup of order q.
  1. C picks random x (1 < x < q), computes e = gx mod p, sends e.
  2. S picks random y (0 < y < q), computes f = gy mod p, K = ey mod p, H = hash(V_C ‖ V_S ‖ I_C ‖ I_S ‖ K_S ‖ e ‖ f ‖ K) and a signature s on H with its private host key. S sends (K_S ‖ f ‖ s).
  3. C verifies that K_S really is S’s host key (certificate or local database), computes K = fx mod p and H, and verifies s. Accepting K_S unverified is allowed but leaves the protocol open to active attacks.

Now both share a master key K; the server is authenticated because it signed its half of the exchange; and H is the session identifier, which never changes even if keys are re-exchanged later.

Key generation

SSH User Authentication and Connection Protocols

With the server authenticated and a protected tunnel in place, the client proves who the user is, then opens as many logical channels as it needs inside the tunnel.

User Authentication Protocol

byte SSH_MSG_USERAUTH_REQUEST (50) string user name authorization identity claimed string service name typically the SSH Connection Protocol string method name … method-specific fields byte SSH_MSG_USERAUTH_FAILURE (51) name-list authentications that can continue boolean partial success byte SSH_MSG_USERAUTH_SUCCESS (52)

FAILURE is sent when the server rejects a request or accepts it but needs more methods.

publickey

The client sends its public key in a message signed with its private key. The server checks that the key is acceptable, then that the signature is correct. Details depend on the public-key algorithm.

password

A plaintext password, protected by the Transport Layer Protocol’s encryption.

hostbased

The client host signs with its own private key, so one host authenticates all its clients. The server verifies the host and believes the host that the user already authenticated on the client side.

Connection Protocol

Runs on the Transport Layer Protocol and assumes a secure authenticated connection, the tunnel, which it uses to multiplex logical channels. Every kind of communication (a terminal session, for example) uses its own channel. Either side may open one; each side gives it a local channel number (the two need not match). Channels are flow controlled by a window: no data may be sent until the receiver indicates window space.

NoteRFC 4254 says the Connection Protocol runs over the Transport Layer and User Authentication protocols; RFC 4251 says over User Authentication. In fact it runs over the Transport Layer Protocol and assumes User Authentication was invoked earlier.

A channel’s life: open (OPEN answered by OPEN_CONFIRMATION, with both channel numbers and the window and packet sizes for incoming traffic, or by OPEN_FAILURE with a reason code), data transfer (CHANNEL_DATA with the recipient channel number, in both directions), close (CHANNEL_CLOSE with the recipient channel number).

Port forwarding

Port — an identifier of a user of TCP. Incoming TCP traffic is delivered to an application by port number; an SMTP server, for example, generally listens on port 25. Port forwarding (SSH tunneling) — converting any insecure TCP connection into a secure SSH connection.

A client application on port x talks to a server application on port y. With SSH, the SSH client and server entities hold a TCP connection on ports a and b; the secure tunnel runs over it. Traffic from port x is redirected to the local SSH entity, crosses the tunnel, and the remote SSH entity delivers it to port y; the reverse direction works the same way.

20.1IP Security Overview

Application-specific mechanisms (S/MIME, Kerberos, TLS) protect only applications that use them. Security at the IP level protects every application, including the many that know nothing about security.

IP Security (IPsec) — security for IP covering three functional areas: authentication (the packet came from the source named in its header and was not altered in transit), confidentiality (encryption against eavesdropping) and key management (secure exchange of keys). Usable with both IPv4 and IPv6, and specified as a set of Internet standards.
IPv4 / IPv6 — the current and next-generation versions of the Internet Protocol. Virtual private network (VPN) — a private network built over a public network such as the Internet, using encryption and authentication so outsiders cannot read or join it. WAN — wide area network.

Applications of IPsec

  • Secure branch office connectivity: a VPN over the Internet or a public WAN, reducing the need for private networks.
  • Secure remote access: a user with IPsec calls a local ISP and reaches the company network securely.
  • Extranet and intranet connectivity with partners: authentication, confidentiality and a key exchange mechanism.
  • Electronic commerce: guarantees that all designated traffic is encrypted and authenticated, adding a layer beneath application-layer security.

What makes this possible: IPsec can encrypt and/or authenticate all traffic at the IP level, so every distributed application (remote logon, client/server, email, file transfer, Web access) is covered.

Benefits of IPsec

  • In a firewall or router it gives strong security for all traffic crossing the perimeter; traffic inside the company incurs no security processing.
  • In a firewall it resists bypass if all outside traffic must use IP and the firewall is the only way in.
  • It sits below the transport layer (TCP, UDP), so it is transparent to applications: no software changes, even when implemented in end systems.
  • It can be transparent to end users: no training, no per-user keying material to issue or revoke.
  • It can protect individual users: off-site workers, or a secure virtual subnetwork for sensitive applications.

Routing applications

IPsec can assure that a router advertisement (a new router announcing itself) and a neighbor advertisement (a router seeking a neighbor relationship in another routing domain) come from authorized routers, that a redirect message comes from the router the original packet was sent to, and that a routing update is not forged. Routing protocols such as OSPF (Open Shortest Path First) should run over IPsec security associations between routers.

IPsec services

A system selects the security protocols, the algorithms and the keys. RFC 4301 lists: access control; connectionless integrity; data origin authentication; rejection of replayed packets (a form of partial sequence integrity); confidentiality (encryption); limited traffic flow confidentiality.

Connectionless integrity (Unit 1) — integrity of each packet on its own, without regard to a larger stream. Traffic flow confidentiality — hiding what could be learned from observing traffic: source, destination, frequency and length.

Transport and tunnel modes

Transport mode

Protects mainly the upper-layer protocols: the IP payload (a TCP or UDP segment, an ICMP packet). Typically end-to-end between two hosts. ESP encrypts and optionally authenticates the payload but not the IP header.

Tunnel mode

Protects the entire IP packet: after the ESP fields are added, the whole packet becomes the payload of a new outer packet with a new outer IP header. No router on the way can examine the inner header, and the outer addresses may be totally different. Used when one or both ends of an SA is a security gateway (a firewall or router running IPsec), so hosts behind it need no IPsec.

Tunnel example: host A sends a packet to host B on another network. A’s firewall decides it needs IPsec, processes it and encapsulates it with an outer header from A’s firewall to B’s firewall. Routers on the way see only the outer header; B’s firewall strips it and delivers the inner packet to B.

20.2IP Security Policy

Every packet that crosses an IPsec boundary is checked against a policy. Two databases decide the outcome: one says what to do with which traffic, the other holds the keys and state to do it.

Security associations

Security association (SA) — a one-way logical connection between a sender and a receiver that affords security services to the traffic carried on it. Two-way secure exchange needs two SAs. An SA is uniquely identified by three parameters:
  • Security Parameters Index (SPI): a 32-bit unsigned integer with local significance only, carried in AH and ESP headers so the receiver can select the SA for a packet.
  • IP Destination Address: the SA’s destination endpoint, an end-user system or a network system such as a firewall or router.
  • Security Protocol Identifier: from the outer IP header; whether the SA is AH or ESP.
Redrawn from Figure 20.2, IPsec architecture.

Security Association Database (SAD)

Every implementation has a nominal SAD (the functionality must exist; how is up to the implementer). An SAD entry holds:

  • SPI: chosen by the receiving end. Outbound: used to build the AH or ESP header. Inbound: maps traffic to the SA.
  • Sequence Number Counter (32 bits) and Sequence Counter Overflow flag (whether overflow is an auditable event that stops the SA).
  • Anti-Replay Window: decides whether an inbound packet is a replay.
  • AH / ESP Information: algorithms, keys, IVs, key lifetimes.
  • Lifetime: time or byte count after which the SA is replaced (new SPI) or terminated.
  • IPsec Protocol Mode: tunnel, transport or wildcard.
  • Path MTU: observed path maximum transmission unit (largest packet sent unfragmented) and aging variables.

Key management is coupled to authentication and privacy only through the SPI, so those mechanisms are specified independently of any key management scheme.

Security Policy Database (SPD)

The nominal SPD relates IP traffic to SAs, or to none for traffic that bypasses IPsec. Each entry is defined by selectors, IP and upper-layer field values that filter outgoing traffic onto an SA:

  • Remote IP address and local IP address: single, list or range, or wildcard (mask). Ranges and wildcards let several systems behind a firewall share one SA.
  • Next layer protocol: the IPv4 Protocol or IPv6 Next Header field value; an individual number, ANY, or (IPv6) OPAQUE.
  • Name: a user identifier from the operating system (available if IPsec runs on the user’s OS).
  • Local and remote ports: individual TCP/UDP ports, a list, or a wildcard.
DMZ — a secure LAN protected by firewalls from both the outside world and the rest of the corporate LAN. /24 — an address range whose first 24 bits are fixed (e.g. 1.2.3.0/24 covers 1.2.3.0–1.2.3.255).

IPsec works packet by packet: outbound packets are processed before transmission, inbound packets after reception and before their contents go to TCP or UDP.

20.3Encapsulating Security Payload

ESP does IPsec’s actual protection. Which services it gives depends on options chosen when the SA is set up and on where in the network it runs.

Encapsulating Security Payload (ESP) — an IPsec header and trailer that can provide confidentiality, data origin authentication, connectionless integrity, an anti-replay service and limited traffic flow confidentiality. It works with many encryption and authentication algorithms, including authenticated encryption such as GCM.

  • SPI: identifies the SA. Sequence Number: monotonically increasing counter, for anti-replay.
  • Payload Data: a transport-level segment (transport mode) or IP packet (tunnel mode), protected by encryption.
  • Pad Length: number of pad bytes just before it. Next Header: type of the first header in the payload (an IPv6 extension header or an upper-layer protocol such as TCP).
  • Integrity Check Value (ICV): a whole number of 32-bit words, computed over the ESP packet minus the authentication data field.
  • Inside the payload there may be an IV or nonce, if the algorithm needs one, and in tunnel mode TFC padding (traffic flow confidentiality) after the payload data, before the Padding field.

A combined mode algorithm (authenticated encryption) returns plaintext and a pass/fail integrity result; the separate ICV may then be omitted, with the algorithm encoding an ICV-equivalent inside the Payload Data.

Encryption and authentication algorithms

Payload Data, Padding, Pad Length and Next Header are encrypted. An IV, if needed, may be carried at the start of the Payload Data; it is usually not encrypted, though often called part of the ciphertext. The ICV is optional, present only if integrity is selected, and is computed after encryption:

  • The receiver can detect and reject replayed or bogus packets before decrypting, reducing the impact of DoS attacks.
  • Decryption and integrity checking can run in parallel.
  • The ICV is not encrypted, so a keyed integrity algorithm (a MAC) must compute it.

Padding

  • Expands the plaintext (Payload Data, Padding, Pad Length, Next Header) to a multiple of the cipher’s block size.
  • Right-aligns Pad Length and Next Header in a 32-bit word, so the ciphertext is a multiple of 32 bits.
  • Extra padding can give partial traffic-flow confidentiality by hiding the real payload length.

Anti-Replay Service and ESP Modes

IP may deliver packets out of order or not at all, so the receiver cannot demand strictly increasing sequence numbers. A sliding window tolerates reordering while still catching duplicates.

Replay attack — an attacker obtains a copy of an authenticated packet and later transmits it to the intended destination; duplicate authenticated packets may disrupt service or have other unwanted effects.

Sender: on a new SA the counter starts at 0 and is incremented for each packet, so the first value used is 1. With anti-replay on (the default) the counter must not cycle past 232 − 1 back to zero; at the limit the sender ends the SA and negotiates a new one with a new key.

Receiver: a window of size W (default 64). Its right edge is N, the highest sequence number received so far in a valid packet; slots N − W + 1 to N are marked when correctly received.

  1. Inside the window and new: check the MAC; if authenticated, mark the slot.
  2. Right of the window and new: check the MAC; if authenticated, advance the window so this number is the right edge, and mark it.
  3. Left of the window, or authentication fails: discard; this is an auditable event.

Transport mode operation

IPv4: the ESP header goes just before the transport-layer header, the ESP trailer (Padding, Pad Length, Next Header) after the packet, the authentication data after the trailer. The segment plus trailer are encrypted; authentication covers the ciphertext plus the ESP header. IPv6: ESP is an end-to-end payload placed after the base header and the hop-by-hop, routing and fragment extension headers; the destination options header may go before or after it. 1. The source encrypts trailer plus segment and replaces the plaintext. 2. Routers process the IP header and plaintext extension headers only. 3. The destination uses the SPI to decrypt. Drawback: traffic analysis is possible.

Tunnel mode operation

The ESP header is prefixed to the whole packet, which is encrypted with the trailer. Routers could not process an encrypted header, so the block is wrapped in a new IP header with enough for routing but not for traffic analysis. 1. The source builds the inner packet to the target host, adds ESP, encrypts, and wraps it in an outer header addressed to the firewall. 2. Routers process only the outer header. 3. The destination firewall uses the SPI to decrypt and sends the inner packet on. 4. Internal routers deliver it. Relieves internal hosts of encryption, reduces the keys needed, and thwarts traffic analysis based on the ultimate destination.

20.4Combining Security Associations

An SA implements AH or ESP but not both, and one flow may need protection both host-to-host and gateway-to-gateway. Several SAs then apply to the same traffic.

Security association bundle — a sequence of SAs through which traffic must be processed to provide a desired set of IPsec services. Its SAs may end at the same or different endpoints.

Transport adjacency

More than one security protocol on the same IP packet without tunneling. Only one level of combination: further nesting adds nothing, since all processing happens at one IPsec instance, the ultimate destination.

Iterated tunneling

Multiple layers of security protocols through IP tunneling. Allows many levels of nesting, since each tunnel can start or end at a different IPsec site along the path.

The two can be combined: a transport SA between hosts can travel part of the way through a tunnel SA between gateways.

Authentication plus confidentiality

ESP with authentication option

Apply ESP, then append the authentication data. Transport mode: encryption and authentication cover the IP payload, not the IP header. Tunnel mode: authentication covers the whole packet delivered to the outer destination (e.g. a firewall), which checks it; the inner packet is encrypted for the inner destination. Authentication applies to the ciphertext.

Transport adjacency

Two bundled transport SAs: inner ESP (no authentication option), outer AH. Authentication covers the ESP plus the original IP header except mutable fields, so more fields (including source and destination addresses) are covered. Cost: two SAs instead of one.

Transport-tunnel bundle

Authentication before encryption: inner AH transport SA, outer ESP tunnel SA. The authentication data are then encrypted, so nobody can alter them undetected, and they can be stored with the plaintext message for later reference without re-encrypting.

Basic combinations

The IPsec Architecture document lists four combinations compliant hosts and gateways must support. Each SA can be AH or ESP; host-to-host SAs may be transport or tunnel, all others must be tunnel mode.

20.5Internet Key Exchange

Two applications typically need four keys: a transmit and a receive key for integrity, and the same for confidentiality. IKE creates and distributes them.

Manual

An administrator configures each system with its own keys and those of the systems it talks to. Practical for small, static environments.

Automated

On-demand creation of keys for SAs; suits large distributed systems with changing configurations.

The default automated protocol was ISAKMP/Oakley:

Oakley Key Determination Protocol — a key exchange protocol based on Diffie–Hellman with added security; generic, it dictates no formats. Internet Security Association and Key Management Protocol (ISAKMP) — a framework for Internet key management with the formats for negotiating security attributes; it does not dictate a key exchange algorithm but defines message types that allow many.

IKEv2 no longer uses the terms Oakley and ISAKMP and differs significantly from IKEv1, but the basic functionality is the same. The rest of this section is IKEv2.

Key determination protocol

A refinement of Diffie–Hellman. Global parameters: a large prime q and a primitive root α of q. A picks private XA and sends YA = αXA mod q; B does the same; both compute K = YBXA mod q = YAXB mod q.

Primitive root (Unit 2) — a number whose powers mod q produce every nonzero residue mod q.

Attractive features

Secret keys are created only when needed, not stored for long. No infrastructure beyond agreement on the global parameters.

Weaknesses

No information about the parties’ identities. Open to a man-in-the-middle attack. Computationally intensive, so open to a clogging attack: an opponent requests many keys and the victim wastes resources on useless modular exponentiation.

Features of IKE key determination

  1. Cookies thwart clogging attacks.
  2. The two parties negotiate a group: the global parameters of the DH exchange.
  3. Nonces ensure against replay attacks.
  4. It enables the exchange of DH public key values.
  5. It authenticates the DH exchange to thwart man-in-the-middle attacks.

Clogging: the opponent forges a legitimate user’s source address and sends DH public keys; each one costs the victim a modular exponentiation. The cookie exchange has each side send a pseudorandom cookie in its first message, which the other side acknowledges and must repeat in the first DH message. With a forged source address the opponent never receives the cookie, so it can only make the victim send acknowledgments, not compute DH.

  1. The cookie must depend on the specific parties, so a cookie obtained with a real address and UDP port cannot be reused from random addresses.
  2. Only the issuer can generate cookies it will accept: it uses local secret information that cannot be deduced from any cookie, so it need not store issued cookies.
  3. Generation and verification must be fast.

Digital signatures

Each party signs a mutually obtainable hash of parameters such as user IDs and nonces with its private key.

Public-key encryption

Parameters such as IDs and nonces are encrypted with the sender’s private key.

Symmetric-key encryption

A key derived out of band encrypts exchange parameters.

IKEv2 exchanges

Messages come in pairs. The first exchange agrees algorithms and parameters and swaps nonces and DH values, creating the IKE SA: a secure channel protecting all later IKE messages with encryption and message authentication. The second exchange authenticates both parties and sets up the first IPsec SA in the SADB. So four messages create the first SA for general use. IKE Header and Payload Formats

IKE’s formats are independent of the key exchange protocol, encryption algorithm and authentication mechanism, so the same framework carries any of them.

An IKE message is an IKE header followed by one or more payloads, carried in a transport protocol; implementations must support UDP.

20.6Cryptographic Suites

IPsec and IKE each need several algorithm types, each with parameters. Recommended suites fix a compatible set so implementations interoperate.

RFC 4308 defines two VPN suites: VPN-A matches the corporate VPN security of older IKEv1 implementations; VPN-B is stronger and recommended for new VPNs with IPsecv3 and IKEv2. RFC 6379 defines four optional suites compatible with the NSA’s Suite B (algorithms and strengths for sensitive but unclassified and classified information), differing in strength and in whether ESP gives confidentiality plus integrity or integrity only. All four are stronger than the VPN suites.

17.1 What are the advantages of each of the three approaches shown in Figure 17.1?
  • Network level (IPsec): transparent to end users and applications; a general-purpose solution; its filtering means only selected traffic incurs IPsec overhead.
  • Transport level (SSL/TLS): relatively general-purpose; can be part of the protocol suite and so transparent to applications, or embedded in packages such as browsers and servers.
  • Application level: the service can be tailored to the specific needs of a given application.
17.2 What protocols comprise TLS?

The Record Protocol, and above it the Handshake Protocol, the Change Cipher Spec Protocol and the Alert Protocol. The Heartbeat Protocol, defined in a separate RFC, also runs over the Record Protocol.

17.3 What is the difference between a TLS connection and a TLS session?

A connection is a transient, peer-to-peer transport providing a suitable type of service; each is associated with one session. A session is an association between client and server, created by the Handshake Protocol, that defines cryptographic parameters shared by many connections, so they need not be renegotiated for each connection.

17.4 List and briefly define the parameters that define a TLS session state.
  • Session identifier: chosen by the server to identify an active or resumable session.
  • Peer certificate: the peer’s X.509v3 certificate; may be null.
  • Compression method: algorithm used to compress data before encryption.
  • Cipher spec: bulk encryption and MAC hash algorithms, plus attributes such as hash_size.
  • Master secret: 48-byte secret shared by client and server.
  • Is resumable: whether the session can start new connections.
17.5 List and briefly define the parameters that define a TLS session connection.
  • Server and client random: byte sequences chosen by each side for each connection.
  • Server / client write MAC secret: MAC key for data each side sends.
  • Server / client write key: encryption key for data each side encrypts.
  • Initialization vectors: one per key for CBC; then the last ciphertext block of each record.
  • Sequence numbers: separate send and receive counters, reset on change cipher spec, at most 264 − 1.
17.6 What services are provided by the TLS Record Protocol?
  • Confidentiality: conventional encryption of payloads with a shared key defined by the Handshake.
  • Message integrity: a MAC with another shared key defined by the Handshake.
17.7 What steps are involved in the TLS Record Protocol transmission?
  1. Fragment the application data into blocks of at most 214 bytes.
  2. Optionally compress.
  3. Compute and append a MAC (HMAC over sequence number, type, version, length and fragment).
  4. Encrypt, with padding for block ciphers.
  5. Prepend the header: content type, major and minor version, compressed length.
  6. Send in a TCP segment.
17.8 Give brief details about different level of awareness of a connection in HTTPS.
  • HTTP level: the client requests a connection to the HTTP server from the next lowest layer (TCP or TLS).
  • TLS level: a session between TLS client and server; it can support one or more connections.
  • TCP level: a TLS connection request begins with a TCP connection between the TCP entities on each side.
17.9 Which protocol was replaced by SSH and why? Which version is currently in the process of being standardized?

SSH replaced TELNET and other remote logon schemes because they provided no security. SSH2, which fixes security flaws in SSH1, is documented as a proposed standard in RFCs 4250–4256.

17.10 List and briefly define the SSH protocols.
  • Transport Layer Protocol: server authentication, data confidentiality and integrity with forward secrecy; optional compression.
  • User Authentication Protocol: authenticates the user to the server.
  • Connection Protocol: multiplexes multiple logical channels over one SSH connection.

Chapter 20

20.1 List and briefly describe some benefits of IPsec.
  • In a firewall or router: secures all traffic crossing the perimeter, with no overhead for internal traffic.
  • In a firewall: resists bypass if the firewall is the only entry from the Internet.
  • Below the transport layer: transparent to applications.
  • Transparent to end users: no training, no per-user keys to issue or revoke.
  • Can secure individual users: off-site workers, or a virtual subnetwork for sensitive applications.
20.2 List and briefly define different categories of IPsec documents.
  • Architecture: concepts, requirements, mechanisms (RFC 4301).
  • Authentication Header: message authentication (RFC 4302); deprecated.
  • Encapsulating Security Payload: encryption or combined encryption/authentication (RFC 4303).
  • Internet Key Exchange: key management (RFC 7296).
  • Cryptographic algorithms: encryption, message authentication, PRFs, key exchange.
  • Other: security policy, MIB content.
20.3 What parameters identify an SA and what parameters characterize the nature of a particular SA?
  • Identified by: the Security Parameters Index, the IP destination address and the security protocol identifier (AH or ESP).
  • Characterized by its SAD entry: sequence number counter, sequence counter overflow, anti-replay window, AH information, ESP information, lifetime, IPsec protocol mode and path MTU.
20.4 What is the difference between transport mode and tunnel mode?
  • Transport mode: protects the IP payload (upper-layer data), typically end to end between hosts; the IP header is not encrypted.
  • Tunnel mode: protects the entire IP packet by encapsulating it with the security fields in a new outer packet; used when one or both ends of the SA is a security gateway; hides the inner header from routers on the way.
20.5 What are the types of secret key algorithm used in IPsec?
  • Encryption: e.g. CBC mode in the VPN suites, AES-GCM for ESP in Suite B.
  • Message authentication: e.g. HMAC-SHA1-96, AES-XCBC-MAC-96, GMAC, HMAC-SHA-256/384.
  • Pseudorandom function: IKEv2 reuses its MAC repeatedly.
20.6 Why does ESP include a padding field?
  • To expand the plaintext to a multiple of the cipher’s block size.
  • To right-align Pad Length and Next Header in a 32-bit word, so the ciphertext is a multiple of 32 bits.
  • With extra padding, to give partial traffic-flow confidentiality by hiding the payload length.
20.7 What are the basic approaches to bundling SAs?
  • Transport adjacency: more than one security protocol on the same packet without tunneling; one level only.
  • Iterated tunneling: multiple layers of security protocols through IP tunneling; nesting possible because each tunnel can start or end at a different IPsec site.

The two can be combined.

20.8 What are the roles of the Oakley key determination protocol and ISAKMP in IPsec?

Together they were IPsec’s default automated key management (ISAKMP/Oakley):

  • Oakley: the key exchange protocol, based on Diffie–Hellman with added security; dictates no formats.
  • ISAKMP: the framework, message types and formats for negotiating security attributes, independent of the key exchange algorithm.

IKEv2 drops both names but keeps the same functions.
