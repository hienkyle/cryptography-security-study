Key Management & Authentication

Every cipher so far assumed the parties already hold the right keys. Chapter 14 covers how they get them: key distribution centers and key hierarchies for secret keys, public-key methods for sending secret keys, and certificates, X.509 and PKI for trusting public keys. Chapter 15 uses the same tools to prove who a user is across a network: nonces and timestamps against replay, Kerberos tickets, public-key protocols, federated identity and PIV smart cards.

14.1Symmetric Key Distribution Using Symmetric Encryption

Both parties must share a key that no one else sees, and keys should change often to limit what one stolen key exposes. So the strength of a cryptographic system rests on how keys are delivered.

Key distribution technique — the means of delivering a key to two parties who wish to exchange data, without allowing others to see the key.

For parties A and B there are four ways:

  1. A selects a key and physically delivers it to B.
  2. A third party selects the key and physically delivers it to A and B.
  3. If A and B recently shared a key, one sends the new key encrypted with the old key.
  4. If A and B each have an encrypted connection to a third party C, C delivers the key over those links.
Link encryption — each communication link is protected by an encryption device at each of its ends; a device only ever talks to its partner on the other end. End-to-end encryption — encryption is applied between the two end systems (hosts, processes or applications), across the whole network path.
  • Options 1 and 2 (manual delivery) are reasonable for link encryption but awkward for end-to-end encryption, where a host may talk to many hosts over time.
  • Option 3: if an attacker ever gets one key, every later key is revealed; and the first keys still have to be delivered somehow.
  • Option 4, in the form of a key distribution center, is the widely adopted choice for end-to-end encryption.
Lab · How many keys?Figure 14.1

Pairwise keys grow as N(N − 1)/2, a straight line of slope 2 on a log-log scale. With a KDC only N master keys are needed. Node-level encryption over 1000 nodes needs about half a million keys; 10 000 applications need about 50 million.

The key hierarchy

Key distribution center (KDC) — a trusted party that distributes keys to pairs of users (hosts, processes, applications) as needed. Each user shares a unique key with the KDC for this purpose.
Session key — a temporary key that encrypts traffic between end systems, typically for the duration of one logical connection (for example a transport connection), then discarded. It is obtained from the KDC over the same network, so it travels encrypted.
Master key — the long-term key each end system or user shares with the KDC, used to encrypt session keys in transit. N entities need only N master keys, so they can be distributed non-cryptographically (e.g. physical delivery).
Redrawn from Figure 14.2, The use of a key hierarchy.
Nonce — a value used once to identify one transaction: a timestamp, counter or random number. It must differ with each request and, to stop masquerade, be hard for an opponent to guess, so a random number is a good choice.

Hierarchical key control

A large network can use a hierarchy of KDCs: a local KDC for each small domain (a LAN, a building), and a global KDC through which local KDCs talk when entities in different domains need a shared key (any of the three may pick the key). This minimizes master-key distribution, since most master keys are shared only with a local KDC, and limits a faulty or subverted KDC’s damage to its own area. It extends to three or more layers.

Session key lifetime

Frequent changes give an opponent less ciphertext per key, but each distribution delays the exchange and loads the network.

Protocol data unit (PDU) — the block of data a protocol layer sends as one unit (a packet or segment), usually numbered with a sequence number.
  • Connection-oriented protocols: one session key per connection; on a very long connection, change it periodically, e.g. each time the PDU sequence number cycles.
  • Connectionless (transaction-oriented) protocols: a new key per exchange is most secure but destroys their low overhead; better to use a key for a fixed period or a fixed number of transactions.

A transparent key control scheme

Session security module (SSM) — functionality at one protocol layer that performs end-to-end encryption and obtains session keys on behalf of its host or terminal, so the end users never see key handling. Assumes a connection-oriented protocol such as TCP.

Decentralized key control

Without a KDC there is no central party to trust or protect, but each end system must talk securely with every partner: up to n(n − 1)/2 master keys in total, at most n − 1 per node. Practical only in a local context. Messages under the master key are short, so cryptanalysis is difficult; session keys are still used only for a limited time.

Controlling Key Usage

Separating keys by purpose stops one kind of key being misused as another, for instance a master key being treated as a session key.

Session keys can be split by use: a data-encrypting key (general network traffic), a PIN-encrypting key (personal identification numbers in electronic funds transfer and point-of-sale) and a file-encrypting key (files in publicly accessible places).

Risk: master keys are kept inside the cryptographic hardware, while session keys encrypted under them (and data encrypted under those) are available to applications. If a master key is imported into a device as a data-encrypting key, an unauthorized application may be able to recover plaintext session keys encrypted with that master key.

Key tags

For DES, the 8 non-key (parity) bits of each 64-bit key become a tag: one bit says session or master key, one says whether encryption is allowed, one whether decryption is allowed; the rest are spare. The tag is encrypted along with the key when it is distributed. Drawbacks: only 8 bits, and because the tag is not in the clear it can be checked only at the point of decryption.

Control vectors

Control vector (CV) — a variable-length set of fields attached to each session key that specifies the uses and restrictions for that key. It is cryptographically coupled to the key when the KDC generates it, and travels in the clear.
H = h(CV)hash; output length = key length Key input = Km ⊕ H Ciphertext = E([Km ⊕ H], Ks)sent with the CV in clear Ks = D([Km ⊕ H], E([Km ⊕ H], Ks))recovery needs Km and the CV
Hash function (Unit 7) — maps values from a larger range into a smaller range with a reasonably uniform spread; here it shrinks the CV to key length.

The session key can be recovered only with both the master key and the exact control vector, so the CV and the key stay linked. Advantages over the 8-bit tag: no length limit (arbitrarily complex controls), and the CV is in the clear at every stage, so key use can be checked in many places.

14.2Symmetric Key Distribution Using Asymmetric Encryption

Public-key encryption is too slow for bulk data, so one of its most important jobs is encrypting small secret keys for distribution.

Simple secret key distribution

A creates a fresh key pair {PUa, PRa}, sends PUa ‖ IDA; B returns E(PUa, Ks); A recovers Ks = D(PRa, E(PUa, Ks)); A discards both keys of the pair and B discards PUa. No keys exist before or after, so compromise risk is minimal and eavesdroppers learn nothing.

Man-in-the-middle attack — an adversary who controls the channel intercepts messages and relays or substitutes them, so each side believes it is talking to the other.

After the attack D only eavesdrops, decrypting everything with Ks. The simple protocol is safe only when the sole threat is eavesdropping.

A hybrid scheme

A KDC still shares a master key with each user and sends session keys encrypted under it, but the master keys themselves are distributed with public-key encryption: a three-level hierarchy (public key → master key → session key).

  • Performance: session keys change often in transaction-oriented applications; public-key work is used only occasionally, to update a master key.
  • Backward compatibility: easily overlaid on an existing KDC scheme with minimal disruption.

14.3Distribution of Public Keys

A public key need not be secret, but it must be genuine. Each scheme below trades convenience against how hard it is to plant a forged key.

Public announcement

Anyone broadcasts their key (e.g. appended to forum posts). Weakness: anyone can forge an announcement “from A” and read A’s mail until the forgery is discovered.

Publicly available directory

A trusted authority keeps {name, public key} entries. Weakness: steal the authority’s private key, or tamper with its records, and you can hand out counterfeit keys.

Public-key authority

Tighter control: the authority answers each request, signed. Weakness: a bottleneck, and its directory can still be tampered with.

Public-key certificates

A signed {key, owner ID} block that participants exchange directly, as reliable as asking the authority.

The directory scheme: (1) the authority keeps an entry per participant; (2) participants register in person or by secure authenticated communication; (3) a key can be replaced at any time (heavy use, or a compromised private key); (4) electronic access requires secure, authenticated communication from the authority.

Public-key authority

Each participant reliably knows the authority’s public key PUauth; only the authority knows PRauth.

Seven messages, but the first five are needed only rarely: A and B cache each other’s keys and periodically request fresh copies.

Public-key certificates

Certificate authority (CA) — a trusted third party (e.g. a government agency or financial institution) that signs certificates. Public-key certificate — a public key and an identifier of its owner, with the whole block signed by the CA.

Requirements: (1) anyone can read a certificate to learn the owner’s name and key; (2) anyone can verify it came from the CA and is not counterfeit; (3) only the CA can create and update certificates; (4) anyone can verify its time validity.

CA = E(PRauth, [T ‖ IDA ‖ PUa])issued to A D(PUauth, CA) = (T ‖ IDA ‖ PUa)anyone verifies

Only PUauth opens the certificate, proving the CA made it. The timestamp T acts like an expiration date: if A’s private key is stolen and A gets a new certificate, the adversary could replay the old certificate to B; an old enough certificate is treated as expired.

14.4X.509 Certificates

X.509 is the universally accepted certificate format, used by IPsec, TLS and S/MIME (Units 11–12).

X.500 directory — a server or distributed set of servers holding a database of user information, including a mapping from user name to network address. ITU-T X.509, part of the X.500 series, defines how this directory provides authentication services, mainly as a repository of public-key certificates.

X.509 relies on public-key cryptography and digital signatures but does not dictate a signature algorithm or hash function. The CA hashes the unsigned certificate and signs the hash with its private key (with RSA this is “encrypting the hash”; with DSA or ECDSA the hash is input to signature generation instead).

Anyone with the CA’s public key can verify the certified key, and no one but the CA can modify a certificate undetected. So certificates are unforgeable and can sit in a directory with no special protection, or be sent directly between users.

Certificate Chains, Revocation and Version 3

With many users there are many CAs, each giving its public key securely to some fraction of users. Chains let a user trust a key certified by a CA it has never met.

If A trusts X1 and B’s certificate comes from X2, and the two CAs have exchanged keys: A gets X1<<X2>> (verifiable with X1’s key, yielding X2’s key), then X2<<B>>. In general X1<<X2>> X2<<X3>> … XN<<B>>, where each adjacent pair of CAs has certified the other. X.509 suggests arranging CAs in a hierarchy so paths are easy to find.

Forward certificates — certificates of CA X generated by other CAs. Reverse certificates — certificates generated by X for other CAs. A CA’s directory entry holds both.

Revoking certificates

A certificate normally lapses at the end of its validity period and is replaced just before. It may be revoked early because (1) the user’s private key is assumed compromised, (2) the user is no longer certified by this CA (name change, certificate superseded, not issued per policy), or (3) the CA’s certificate is assumed compromised.

Certificate revocation list (CRL) — a list, signed by the CA and posted in the directory, of all revoked but unexpired certificates it issued (to users and to other CAs). It contains the issuer name, this update date, next update date, and one entry per revoked certificate: serial number and revocation date (serial numbers are unique within a CA, so they suffice). Figure 14.15b.

A user receiving a certificate must check that it is not revoked; to avoid directory searches each time, users usually keep a local cache of certificates and CRLs.

X.509 version 3

Version 2 could not carry identities beyond short X.500 names (e.g. email addresses, URLs), security policy information, limits on what a faulty or malicious CA’s certificates can be used for, or which of an owner’s keys over time this is. Version 3 adds optional extensions instead of more fixed fields.

Extension — an extension identifier, a criticality indicator and a value. If the indicator is TRUE and an implementation does not recognize the extension, it must treat the certificate as invalid.
Certificate policy — a named set of rules that says which community and/or class of application with common security requirements a certificate applies to.

14.5Public-Key Infrastructure

Certificates need people, systems and procedures around them. PKIX is the IETF model for running them on the Internet.

Public-key infrastructure (PKI) (RFC 4949) — the hardware, software, people, policies and procedures needed to create, manage, store, distribute and revoke digital certificates based on asymmetric cryptography. Goal: secure, convenient, efficient acquisition of public keys. PKIX is the IETF Public Key Infrastructure X.509 working group’s model.
  • End entity: end user, device (server, router) or anything identifiable in a certificate’s subject field.
  • Certification authority (CA): issues certificates and usually CRLs.
  • Registration authority (RA): optional; takes over administrative functions from the CA, often end-entity registration.
  • CRL issuer: optional; publishes CRLs for a CA.
  • Repository: any method of storing certificates and CRLs for retrieval.

Management protocols

  • Certificate management protocols (CMP), RFC 2510: each management function has explicit protocol exchanges; flexible for many technical, operational and business models.
  • Certificate management messages over CMS (CMC), RFC 2797, where CMS is the cryptographic message syntax (RFC 2630): built on earlier work to reuse existing implementations; all functions supported, but not all as specific exchanges.
Current practiceThe RFCs the book cites have been replaced: CMP is now RFC 9810 (2025; it obsoletes RFC 4210, which replaced RFC 2510), CMC is RFC 5272 (updated by RFC 6402), and the Internet X.509 certificate and CRL profile is RFC 5280.

15.1Remote User-Authentication Principles

User authentication is the primary line of defense: access control and accountability both depend on knowing who the user is.

User authentication (RFC 4949) — verifying an identity claimed by or for a system entity, in two steps. Identification step: presenting an identifier (e.g. user ID ABTOKLAS; not secret). Verification step: presenting or generating authentication information (e.g. a password; secret) that corroborates the binding between entity and identifier.

User authentication differs from message authentication (Unit 7), which verifies that a received message is unaltered and from its claimed source.

The NIST model (SP 800-63-2)

Electronic user authentication — establishing confidence in user identities presented electronically to an information system.
  • Applicant applies to a registration authority (RA), a trusted entity that establishes and vouches for the applicant’s identity to a credential service provider (CSP); the applicant becomes a subscriber.
  • Token: something the subscriber possesses (an encryption key or an encrypted password).
  • Credential: a data structure that authoritatively binds an identity and attributes to a token; verifiable in an authentication transaction.
  • Claimant: the party to be authenticated. Verifier: the party checking that the claimant controls the token. The verifier sends an assertion about the subscriber to the relying party (RP), which makes access control decisions.
Simplified from Figure 15.1. Dashed: the verifier validates the token and credential with the CSP.

Means of authentication

Something the individual knows

Password, PIN, answers to prearranged questions. Can be guessed, stolen or forgotten.

Something the individual possesses

Cryptographic keys, keycards, smart cards, physical keys: a token. Can be forged, stolen or lost.

Something the individual is

Static biometrics: fingerprint, retina, face.

Something the individual does

Dynamic biometrics: voice pattern, handwriting, typing rhythm.

Biometrics bring false positives and negatives, user acceptance, cost and convenience problems; all methods carry administrative overhead. Over a network, the most important methods are cryptographic keys and something the user knows.

Mutual authentication

Mutual authentication protocol — lets the communicating parties satisfy themselves about each other’s identity and exchange session keys. Two central issues: confidentiality (identification and session-key data must travel encrypted, which needs existing secret or public keys) and timeliness (against replays).
Replay attack — an opponent re-sends a previously captured valid message. At worst it compromises a session key or impersonates a party; at least it disrupts operations with genuine-looking messages.

Kinds of replay ([GONG93]):

  1. Copy a message and replay it later.
  2. Replay a timestamped message inside its valid time window; if original and replay both arrive, it can be logged.
  3. Same as 2, but suppress the original, so the repetition cannot be detected.
  4. Backward replay without modification: replay to the sender, possible with symmetric encryption when the sender cannot tell sent from received messages by content.
CountermeasureHowDrawback
Sequence numbersAccept only messages in proper order.Each party must track the last number for every claimant; generally not used.

One-way authentication

Email is the main case: sender and receiver need not be online together. The header must stay in the clear for the store-and-forward protocol (e.g. SMTP or X.400), the body should be encrypted so the mail system does not hold the key, and the recipient wants assurance of the sender.

Current practiceSP 800-63-2 has been superseded by SP 800-63-3 (2017) and now SP 800-63-4 (final, 2025), which keeps the same roles (CSP, subscriber, claimant, verifier, relying party).

15.2Remote User-Authentication Using Symmetric Encryption

KDC protocols both distribute session keys and authenticate. Each fix below closes a replay hole, and some open a new one, which shows how hard these protocols are to get right.

Notation: “A → B: X” means A sends X to B; f() is a generic function that modifies a nonce (e.g. adds 1).

Needham–Schroeder

The Figure 14.3 protocol. Step 4 shows B knows Ks; step 5 shows A knows Ks and that the message is fresh.

Weakness: an opponent X who has compromised an old session key replays step 3. Unless B remembers every old session key with A, B cannot tell, and X answers the handshake and sends bogus messages as A.

Denning: add timestamps

T assures A and B that Ks was just generated. Each checks

|Clock − T| < Δt1 + Δt2 Δt1 = normal discrepancy between KDC clock and local clock Δt2 = expected network delay

T is encrypted under the secure master keys, so even with an old session key a replayed step 3 is rejected as untimely. But this relies on clocks synchronized across the network.

Suppress-replay attack — when a sender’s clock is ahead of the recipient’s, an opponent intercepts (and suppresses) a message and replays it later, when its timestamp becomes current at the recipient.
Lab · Timestamp window and suppress-replay§15.2

Colours show the outcome security wants: blue is correct (an honest message accepted, a replay blocked), red is a failure. The sender stamps T from its own clock at recipient time 0; the original arrives about 0.5 min later. If the sender’s clock is ahead by more than the window, the honest original is rejected while a held replay can be accepted.

Counters: make parties regularly check clocks against the KDC’s; or use nonce handshakes, which cannot be suppress-replayed because the recipient’s future nonces are unpredictable.

Neuman–Stubblebine (nonces + a ticket)

Tb is relative to B’s clock and only B checks it, so no clock synchronization is needed. The block E(Kb, [IDA ‖ Ks ‖ Tb]) is a ticket A can reuse until Tb to start new sessions with B without contacting the KDC (second variant).

15.3Kerberos

Kerberos is a widely used authentication service for an open distributed network: users at workstations who need services on many servers.

A workstation cannot be trusted to identify its users. Three threats:

  1. A user at a workstation pretends to be another user.
  2. A user alters a workstation’s network address so requests appear to come from another workstation.
  3. A user eavesdrops and uses a replay attack to gain entry or disrupt operations.

Three possible approaches: (1) trust each client to identify its users and each server to enforce policy by user ID; (2) clients authenticate themselves to servers, but are trusted about who their user is; (3) users prove their identity for every service, and servers prove theirs to clients. Kerberos supports (3), using one or more Kerberos servers that provide authentication; it is a trusted third party based on the Needham–Schroeder protocol.

Secure

An eavesdropper cannot get what is needed to impersonate a user; Kerberos is never the weak link.

Reliable

Services depend on it, so it uses a distributed server architecture with backups.

Transparent

Beyond entering a password, the user is unaware of authentication.

Scalable

Supports large numbers of clients and servers: a modular, distributed design.

A simple authentication dialogue

Authentication server (AS) — knows every user’s password (central database) and shares a unique secret key with each server. Ticket — a block encrypted with a key the client does not hold, so the client can carry it but not alter or forge it.
  • IDV in the ticket lets V check it decrypted the ticket properly; IDC says on whose behalf it was issued.
  • ADC (network address) stops an opponent who captures the ticket from using it from another workstation.
  • Problems: a password for every ticket (and a new ticket per service), and the password crosses the network in plaintext in message (1).

A more secure dialogue: the ticket-granting server

Ticket-granting server (TGS) — issues service tickets to users already authenticated by the AS. The ticket-granting ticket (Tickettgs) is reusable for one logon session; each service-granting ticket (Ticketv) is reusable for one service.
  • The AS’s reply is encrypted with Kc, a key derived from the user’s password: only the right user can open it, and the password is never sent.
  • Tickets carry a timestamp and lifetime (e.g. eight hours) so a ticket captured after logoff cannot be reused forever. Tickettgs is encrypted with Ktgs (AS and TGS only); Ticketv with Kv (TGS and V only).
  • Result: one password query per user session, and the password is protected.

The Kerberos Version 4 Dialogue

Two problems remain. A captured ticket can be used by an opponent before it expires (a short lifetime means repeated password prompts, a long one means more chance to replay). And servers never authenticate themselves to users.

Fix: the AS gives both the client and the TGS a secret, a session key Kc,tgs; the client proves it is the ticket’s owner by using that key in an authenticator.

Authenticator — ID and address of C’s user plus a timestamp, encrypted with the session key. Unlike the reusable ticket, it is used once and has a very short lifetime. The ticket only distributes the key securely (in effect: whoever uses Kc,tgs is C); the authenticator proves identity (in effect: C is using Kc,tgs at time TS3).

Kerberos Realms and Version 5

One Kerberos server serves one administrative domain. Realms and interrealm keys let users reach servers in other organizations.

A full-service Kerberos environment needs: (1) the Kerberos server holds the user ID and hashed password of every user (all users registered); (2) it shares a secret key with every server (all servers registered).

Kerberos realm — a set of managed nodes sharing the same Kerberos database, which lives on a physically secure master system (read-only copies may exist elsewhere; changes need the Kerberos master password). Kerberos principal — a service or user known to Kerberos, named by service or user name, instance name and realm name.

Interrealm authentication adds: (3) the Kerberos servers of the two realms share a secret key and are registered with each other, and trust each other to authenticate their users.

Problem: N realms need N(N − 1)/2 secure key exchanges to all interoperate.

The version 5 dialogue

  • New in message (1): Realm of the user; Options (flags to set in the ticket); Times (from: start, till: expiry, rtime: renew-till); Nonce (repeated in (2) to prove freshness).
  • The authenticator in (5) may carry a Subkey (client’s key for this application session; if omitted, Kc,v is used) and a Sequence number (starting number for the server’s messages, to detect replays). The client may request mutual authentication.
  • Message (6) returns TS2 unchanged: no +1 is needed because the format means no opponent can build (6) without the keys.

15.4Remote User-Authentication Using Asymmetric Encryption

Figure 14.9 assumed each party already has the other’s current public key. These protocols fetch certificates from a central server instead.

Mutual authentication

Denning’s timestamp protocol: the central authentication server (AS) only provides public-key certificates; A chooses and encrypts the session key, so the AS never sees it. Timestamps protect against replays of compromised keys, but clocks must be synchronized.

Woo and Lam use nonces instead. The authors then found a flaw and revised it: IDA is added to the block signed by the KDC in steps 5 and 6.

Why: Na is unique only among A’s own nonces, not among everyone’s, so it is the pair {IDA, Na} that identifies A’s request. Binding IDA and IDB to Ks ties the key to both parties.

  • The one-time key is more efficient than encrypting the whole message with B’s public key.
  • The plain signature stops A denying the message, but Max can take Bob’s message from the mail queue, strip Bob’s signature, attach his own and take credit; encrypting message and signature with the recipient’s public key stops this.
  • The signature schemes need B to know A’s current public key; the certificate (signed by the AS) supplies it. For confidentiality, encrypt everything with B’s public key, or with a one-time key sent under B’s public key (Unit 12).

15.6Personal Identity Verification

Smart-card authentication is spreading; FIPS 201-2 defines a government-wide PIV system that also serves as a guideline for any organization.

Smart card — looks like a credit card but contains a whole microprocessor (processor, memory, I/O ports), sometimes a cryptographic co-processor; contacts or an embedded antenna. ROM: data fixed for the card’s life (card number, cardholder name). EEPROM: application data and programs that can change (e.g. talk time remaining). RAM: temporary data during execution.

PIV system model (Figure 15.8)

  • PIV front end: the physical interface for physical or logical access; up to three-factor authentication. Uses the PIV card (dual contact/contactless), holding a photograph, X.509 certificates, keys, biometric data and the CHUID; some data needs a PIN to read. Biometric reader: fingerprint or iris.
  • PIV card issuance and management: identity proofing and registration, card and key issuance, repositories and services (PKI directory, certificate status servers).
  • Relying subsystem: decides a cardholder’s access to a physical or logical resource; FIPS 201-2 standardizes its interaction with the PIV system.

14.6 · 15.7Review Questions

Review questions 14.1–14.12 and 15.1–15.10 from the book. Answer first, then open to check.

Chapter 14

14.1 Explain why man-in-the-middle attacks are ineffective on the secret key distribution protocol discussed in Figure 14.3.

Everything secret travels under master keys an opponent does not hold: the reply to A is encrypted with Ka and includes A’s original request and nonce N1 (so A detects alteration or replay), and B’s part is encrypted with Kb. An opponent in the middle cannot read Ks, cannot substitute a key of its own (it cannot encrypt under Ka or Kb), and steps 4–5 with nonce N2 under Ks show B that step 3 is not a replay. Unlike Figure 14.8, there is no unauthenticated key the opponent can swap.

14.2 What is the major issue in end to end key distribution? How does the key hierarchy concept address that issue?

Scale: a key is needed for every pair of communicating endpoints, N(N − 1)/2 for N hosts, and far more at application level, all to be distributed dynamically. With a hierarchy, session keys come from a KDC encrypted under master keys, so only N master keys (one per entity) must be distributed by non-cryptographic means such as physical delivery.

14.3 What is a nonce?

A value used once to identify a transaction uniquely, such as a timestamp, counter or random number. It must differ with each request and should be hard to guess; a random number is a good choice.

14.4 What is a key distribution center?

A trusted system that shares a unique master key with each user and distributes session keys to pairs of users (hosts, processes, applications) as needed, encrypted under their master keys.

14.5 What are two different uses of public-key cryptography related to key distribution?

(1) Distributing secret (symmetric) keys: encrypting a session or master key with a public key (14.2). (2) Distributing public keys themselves securely, through authorities and certificates (14.3).

14.6 List four general categories of schemes for the distribution of public keys.

Public announcement, publicly available directory, public-key authority, and public-key certificates.

14.7 Discuss the potential security issues that arise due to public key directory based system.

If an adversary obtains or computes the directory authority’s private key, it can authoritatively hand out counterfeit public keys and then impersonate any participant and eavesdrop on messages to any participant. The adversary could also tamper with the records the authority keeps. Registration and electronic access also need secure, authenticated communication.

14.8 What is a public-key certificate?

A public key and an identifier of the key owner (plus validity information), with the whole block signed by a trusted third party, the certificate authority.

14.9 What are the requirements for the use of a public-key certificate scheme?

Any participant can read a certificate to learn the owner’s name and public key; any participant can verify that it came from the CA and is not counterfeit; only the CA can create and update certificates; any participant can verify the certificate’s time validity.

14.10 What is the purpose of the X.509 standard?

It defines a framework for authentication services by the X.500 directory: a standard certificate format (and CRL format) for public-key certificates signed by trusted CAs, plus authentication protocols based on them. The format is used by S/MIME, IPsec and SSL/TLS.

14.11 What is a chain of certificates?

A sequence X1<<X2>> X2<<X3>> … XN<<B>> in which each CA certifies the next. Starting from a CA whose key you trust, each certificate yields a verified key for the next CA, ending with a trusted copy of B’s public key.

14.12 How is an X.509 certificate revoked?

The CA adds the certificate’s serial number and revocation date to its certificate revocation list, which it signs and posts in the directory along with its name, the list’s date and the next update date. Users check certificates they receive against the CRL (often a locally cached copy). Reasons: suspected compromise of the user’s private key, the user no longer certified by the CA, or the CA’s own certificate compromised.

Chapter 15

15.1 What are the steps involved in an authentication process?

The identification step, presenting an identifier to the security system; and the verification step, presenting or generating authentication information that corroborates the binding between the entity and the identifier.

15.2 List three general approaches to dealing with replay attacks.

Sequence numbers (accept only messages in proper order), timestamps (accept only if close enough to current time), and challenge/response (require the reply to contain a nonce just sent).

15.3 What is a suppress-replay attack?

When a sender’s clock is ahead of the recipient’s, an opponent intercepts a timestamped message and replays it later, when the timestamp becomes current at the recipient’s site; suppressing the original means the repetition goes undetected.

15.4 What problem was Kerberos designed to address?

In an open distributed environment where users at workstations access services on servers across the network, servers must restrict access to authorized users and authenticate service requests, but a workstation cannot be trusted to identify its users correctly.

15.5 What are three threats associated with user authentication over a network or Internet?

A user may gain access to a workstation and pretend to be another user; a user may alter a workstation’s network address to impersonate another workstation; and a user may eavesdrop and use a replay attack to gain entrance to a server or disrupt operations.

15.6 List three approaches to secure user authentication in a distributed environment.

Rely on each client workstation to assure its users’ identity and on each server to enforce policy by user ID; require client systems to authenticate themselves to servers while trusting them about their users; require the user to prove identity for each service invoked, and servers to prove their identity to clients.

15.7 What four requirements were defined for Kerberos?

Secure, reliable, transparent and scalable.

15.8 What entities constitute a full-service Kerberos environment?

A Kerberos server, a number of clients and a number of application servers, where the Kerberos server holds the user IDs and hashed passwords of all users and shares a secret key with each server.

15.9 In the context of Kerberos, what is a realm?

A set of managed nodes that share the same Kerberos database, typically one administrative domain; the database lives on a physically secure Kerberos master system.

15.10 What are the mandatory elements to authenticate a PIV card holder?

The mandatory PIV data elements: the PIN, the CHUID, the PIV Authentication Key (key pair and certificate), two fingerprint templates, the electronic facial image, and the asymmetric Card Authentication Key.
