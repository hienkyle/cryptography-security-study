Email Security

Email is the most heavily used network application, and its basic machinery (SMTP and the RFC 5322 format) has no security of its own. This unit first describes how mail moves and how messages are formatted (MIME), then the protections layered on top: S/MIME and PGP protect the message itself, STARTTLS protects the hop between servers, and a family of DNS-based mechanisms (DNSSEC, DANE, SPF, DKIM, DMARC) lets receivers check that mail really comes from the domain it claims.

19.1Internet Mail Architecture

The architecture is defined in RFC 5598. Knowing which component does what tells you where each security mechanism later in the chapter is applied.

Message User Agent (MUA) — the user world: acts for users and user applications inside the email service. Message Handling Service (MHS) — the transfer world: accepts a message from one user and delivers it to one or more others, creating a virtual MUA-to-MUA exchange. The MHS is made of Message Transfer Agents (MTA).

The architecture needs three types of interoperability:

  • User to user: the author’s MUA must format the message so the recipient’s MUA can display it.
  • MUA to MHS: when a message is posted into the MHS, and again when the MHS delivers it to the destination MUA.
  • MTA to MTA: among the MTAs along the transfer path.

Domain Name System (DNS) — a directory lookup service mapping the name of an Internet host to its numerical address (Section 19.6).

Email Protocols

Two kinds of protocol move mail: one carries messages across the Internet from source to destination (SMTP); the other lets a user’s client retrieve mail from a mail server (POP3, IMAP).

Simple Mail Transfer Protocol

SMTP — encapsulates a message in an envelope and relays it from source to destination through multiple MTAs. Specified as RFC 821, currently RFC 5321. Later versions with added commands and extensions are called Extended SMTP (ESMTP).
  • Text-based client/server: the client (sender) contacts the server (next-hop recipient), issues commands describing the message, then sends the message itself.
  • A transfer can be one client/server conversation over one TCP connection, or pass through relays: an SMTP server that receives a message then acts as a client toward the next server.
  • The sender opens the TCP connection (server port 25). Each command is one line: a four-letter code, sometimes followed by an argument. Each command gets exactly one reply, beginning with a three-digit code.

STARTTLS and SUBMISSION

STARTTLS (RFC 3207) — an SMTP service extension that adds confidentiality and authentication between SMTP agents by running SMTP over TLS (Unit 11). The server advertises the option; the client issues the STARTTLS command in the SMTP command stream and both sides set up a TLS connection.
  • Advantage: the server offers SMTP on a single port instead of separate ports for secure and cleartext operation. (Port 465 was previously used for SMTP over SSL.)
  • Similar mechanisms exist for running TLS under IMAP and POP.
SUBMISSION (RFC 6409) — the currently preferred standard for MUA-to-MSA transfer, which historically used SMTP. Derived from SMTP, but uses a separate TCP port and imposes distinct requirements such as access authorization.

Mail access protocols

POP3 · Post Office Protocol

Lets an email client (user agent) download mail from a mail server (MTA). Connects over TCP, typically port 110. The user agent sends a username and password (stored for convenience, or typed each time for stronger security), then issues POP3 commands to retrieve and delete mail.

IMAP · Internet Mail Access Protocol

Also lets a client access mail on a server, over TCP port 143. More complex than POP3: stronger authentication and functions POP3 does not support.

19.2Email Formats

S/MIME is built on MIME, and MIME is built on the traditional text-message format, RFC 822 (current version RFC 5322).

RFC 5322

RFC 5322 (Internet Message Format) — defines the format of text messages sent by email. A message has an envelope (whatever is needed for transmission and delivery) and contents (the object delivered). The standard covers only the contents, but its header fields can be used by the mail system to create the envelope.
  • A message is ASCII text: some number of header lines, a blank line, then unrestricted text (the body).
  • A header line is a keyword, a colon, and the keyword’s arguments; a long line may be split over several lines. Most frequent keywords: From, To, Subject, Date. Message-ID holds a unique identifier for the message.

Multipurpose Internet Mail Extensions

MIME (RFCs 2045–2049) — an extension to the RFC 5322 framework that addresses the problems and limitations of using SMTP (or another transfer protocol) with RFC 5322, while staying compatible with existing RFC 5322 implementations.

Limitations of the SMTP/5322 scheme that MIME addresses:

  1. SMTP cannot transmit executable files or other binary objects; conversion schemes such as UNIX UUencode/UUdecode exist but none is a standard.
  2. SMTP cannot transmit national-language characters: they use 8-bit codes (128 or higher) and SMTP is limited to 7-bit ASCII.
  3. SMTP servers may reject messages over a certain size.
  4. SMTP gateways translating between ASCII and EBCDIC use inconsistent mappings.
  5. SMTP gateways to X.400 networks cannot handle nontextual data in X.400 messages.
  6. Some implementations do not follow RFC 821: they add, delete or reorder CR and LF; truncate or wrap lines over 76 characters; remove trailing white space; pad lines to the same length; or convert tabs into spaces.

The MIME specification has three elements: five new header fields giving information about the body; content formats standardizing multimedia representations; and transfer encodings that protect any content format from alteration by the mail system.

Canonical form

Native form

The body is created in the system’s own format: its native character set and, where appropriate, local end-of-line conventions (e.g., a UNIX-style text file, a Sun raster image, a VMS indexed file, audio held only in memory).

Canonical form

The entire body, including out-of-band information such as record lengths and file attributes, is converted to a universal form standardized for use between systems. The media type dictates the form; conversion may involve character-set conversion, audio transformation, compression and so on.

19.4S/MIME

S/MIME protects the message body end to end, from the author’s MUA to the recipient’s MUA, whatever happens to it on the way.

Authentication

A digital signature (Chapter 13), most commonly RSA with SHA-256:

  1. The sender creates a message.
  2. SHA-256 gives a 256-bit message digest.
  3. The digest is encrypted with RSA under the sender’s private key and appended, with signer-identifying information so the receiver can retrieve the signer’s public key.
  4. The receiver decrypts with the sender’s public key to recover the digest.
  5. The receiver hashes the message itself and compares; a match means the message is authentic.

Confidentiality

Most commonly AES-128 in CBC mode. Each symmetric key, the content-encryption key, is used once: a new random number for every message.

  1. The sender generates the message and a random 128-bit content-encryption key.
  2. The message is encrypted with the content-encryption key.
  3. The key is encrypted with RSA under the recipient’s public key and attached.
  4. The receiver recovers the key with RSA and its private key.
  5. The key decrypts the message.

Why this design:

  • Symmetric algorithms are substantially faster than asymmetric ones for large content, so public-key encryption is used only on the short key.
  • Public-key encryption solves session-key distribution: only the recipient can recover the key bound to the message. No session-key exchange protocol (Chapter 14) is needed, and handshaking would be impractical anyway given email’s store-and-forward nature.
  • One-time keys strengthen the symmetric scheme: little plaintext per key, no relationship among keys. As far as the public-key algorithm is secure, the whole scheme is.

Signing and encryption together

S/MIME allows the two operations in either order.

Sign first, then encrypt

The encryption hides the signer’s identity. It is more convenient to store a signature with the plaintext, and a third party verifying the signature need not deal with the symmetric key.

Encrypt first, then sign

A signature can be verified without exposing the content, useful for automatic verification since no private key is needed. But the recipient cannot relate the signer to the unencrypted content.

Email compatibility

With signing only, the digest is encrypted; with confidentiality, the message plus any signature is encrypted. Either way, part or all of the block is arbitrary 8-bit octets, but many mail systems accept only ASCII text. S/MIME converts the raw binary to printable ASCII, called 7-bit encoding, typically with base64: each group of three octets becomes four ASCII characters.

  • Base64 converts the input blindly, even ASCII text. A message that is signed but not encrypted, if converted whole, is unreadable to a casual observer: a certain level of confidentiality.
  • RFC 5751 recommends 7-bit encoding the original MIME content even when no outer 7-bit encoding is used, so the entity can be handled in any environment unchanged. Example: a trusted gateway removes the encryption but not the signature; if the site’s internal transport is not 8-bit clean, the end recipient can verify the signature only if the original entity was 7-bit data.

Compression

Saves space for transmission and storage. It can be applied in any order relative to signing and encryption. RFC 5751 guidelines:

  • Compressing binary-encoded encrypted data is discouraged: it gives little compression. Base64-encrypted data could benefit.
  • With a lossy compression algorithm and signing, compress first, then sign.

The sending agent decides (1) whether the receiver can decrypt a given algorithm and (2), if the receiver accepts only weakly encrypted content, whether weak encryption is acceptable. S/MIME Messages

S/MIME adds new MIME content types, all named with PKCS (public-key cryptography specifications issued by RSA Laboratories).

Securing a MIME entity

  1. A MIME entity (a whole message except the RFC 5322 headers, or one or more subparts of a multipart message) is prepared by the normal MIME rules and converted to canonical form (for multipart, each subpart in its own canonical form).
  2. The entity plus security-related data (algorithm identifiers, certificates) is processed by S/MIME into a PKCS object.
  3. The PKCS object is treated as message content and wrapped in MIME with appropriate headers; transfer encoding, typically base64, is applied at that point because the object is mostly arbitrary binary.

Exception: in a multipart/signed message, the content of one subpart is not changed by the security process. Unless it is 7-bit, it should be transfer encoded (base64 or quoted-printable) so the signed content cannot be altered.

The application/pkcs7-mime subtype covers four categories, each with an smime-type parameter. The resulting object is represented in Basic Encoding Rules (BER) (ITU-T X.209): arbitrary octet strings, so binary, and base64-encoded in the outer MIME message.

Certificate Processing and Enhanced Services

S/MIME uses X.509 version 3 public-key certificates (Chapter 14). Managers and/or users configure each client with a list of trusted keys and certificate revocation lists: maintaining the certificates is a local responsibility, while the certificates themselves are signed by certification authorities.

User agent role

  • Key generation: the user or an administrative utility MUST be able to generate separate Diffie–Hellman and DSS key pairs and SHOULD be able to generate RSA key pairs. Each pair MUST come from a good source of nondeterministic random input and be protected securely. RSA key pairs SHOULD be 768–1024 bits and MUST NOT be shorter than 512 bits.
  • Registration: the public key must be registered with a certification authority to receive an X.509 certificate.
  • Certificate storage and retrieval: a local list of certificates is needed to verify incoming signatures and encrypt outgoing messages, kept by the user or by a local administrative entity for many users.

Enhanced security services (RFC 2634)

Signed receipts — requested in a SignedData object. The recipient signs the original message plus the sender’s signature and appends the new signature, forming a new S/MIME message: proof of delivery that the originator can show a third party.
Security labels — included in the authenticated attributes of SignedData: security information about the sensitivity of the content. Used for access control, priority (secret, confidential, restricted) or roles (e.g., a patient’s health-care team).
Secure mailing lists — an S/MIME Mail List Agent (MLA) takes one incoming message, performs the recipient-specific encryption for each recipient and forwards it. The originator encrypts once, with the MLA’s public key.
Signing certificates — securely binds a sender’s certificate to their signature through a signing certificate attribute.

19.6DNSSEC

Several email security protocols publish their data in the DNS, so they are only as trustworthy as the DNS answers. DNSSEC makes those answers verifiable.

Domain Name System

DNS is essential to the Internet. MUAs and MTAs use it to find the next-hop mail server: a sending MTA queries the Mail Exchange Resource Record (MX RR) of the recipient’s domain (the right-hand side of the “@”) to find the receiving MTA.

Domain name space — a tree-structured name space identifying resources on the Internet.
DNS database — each node and leaf of the tree names a set of information (IP address, name server, …) held in resource records (RRs); all RRs form a distributed database.
Name servers — server programs holding information about a portion of the name tree and its RRs.
Resolvers — programs that extract information from name servers for client requests, typically an IP address for a domain name.

Key features of the database: a variable-depth hierarchy of names, with the period as level delimiter; a distributed database on DNS servers across the Internet; and distribution controlled by the database: thousands of separately administered zones, with distribution and update controlled by the database software. Dynamic updating lets name servers send updates to other relevant servers, coping with Internet growth and dynamically assigned addresses (e.g., home DSL).

DNS Security Extensions

DNSSEC — end-to-end protection of DNS data by digital signatures created by the responding zone administrators and verified by the recipient’s resolver. There is no need to trust the intermediate name servers and resolvers that cache or route the records. Defined in RFC 4033 (introduction and requirements), RFC 4034 (new resource records) and RFC 4035 (protocol modifications: signed zones, serving and resolving).

DNSSEC protects DNS clients from accepting forged or altered RRs by providing:

  • Data origin authentication: the data came from the correct source.
  • Data integrity verification: the RR content has not been modified.

The zone administrator signs every RRset (all RRs with the same label, class and type) and publishes the signatures and the zone’s public key in the DNS itself. Trust in that key is not built from a third party or a PKI chain, but by starting from a trusted zone, such as the root, and verifying each child’s public key with its parent’s signature down to the answering zone. The trusted zone’s public key is the trust anchor.

19.7DNS-Based Authentication of Named Entities

DANE lets a domain say, in DNSSEC-signed DNS data, which certificate its TLS servers use, instead of relying only on the many certificate authorities.

DANE (RFC 6698) — a protocol that binds X.509 certificates, as used by TLS, to DNS names using DNSSEC, so TLS clients and servers can be authenticated without a certificate authority.

Why: the weakness of the CA system

  • Every browser developer and OS supplier keeps a list of CA root certificates (trust anchors) in a root certificate store; the PKIX procedure traces a certificate back to a root.
  • If any of the hundreds of CAs is compromised, an attacker can get its private key, have certificates issued under false names, or add bogus roots to stores. The global PKI has no limit of scope, so one compromised CA damages the whole system.
  • Some CAs have had poor practices, e.g., issuing wildcard certificates that let the holder issue sub-certificates for any domain anywhere.

DANE replaces reliance on CA security with reliance on DNSSEC: the DNS administrator for a domain is already authorized to give information about the zone, so it can also authoritatively bind the domain name to a certificate used by a host there.

TLSA record

TLSA RR — a DNS record type for authenticating SSL/TLS certificates. It can constrain which CA may vouch for a certificate, or which PKIX end-entity certificate is valid; or state that a service certificate or CA is authenticated directly in the DNS. The server’s domain owner creates a TLSA RR identifying the certificate and its public key; a client receiving an X.509 certificate in TLS negotiation looks up the TLSA RR and matches it as part of certificate validation.

Use of DANE for SMTP

STARTTLS runs SMTP over TLS so the whole message and SMTP envelope are encrypted, but only opportunistically, if both sides support it. Even then TLS is vulnerable:

Downgrade

Attackers strip the TLS capability advertisement so the connection does not use TLS. DANE fix: the presence of a TLSA RR signals that encryption must be used.

Unauthenticated TLS

Self-signed and mismatched certificates are common. DANE fix: the certificate is authenticated with a DNSSEC-signed TLSA RR.

DANE can authenticate both the SMTP submission server the MUA talks to and the TLS connections between MTAs.

Use of DNSSEC for S/MIME

S/MIME messages often carry certificates that authenticate the sender and can be used to encrypt replies, but the receiving MUA must validate the certificate of the purported sender. A proposed SMIMEA DNS RR associates certificates with DNS domain names for this. It has the same format and function as TLSA, but serves MUAs dealing with the domain names in email addresses in the message body, not those in the outer SMTP envelope.

19.8Sender Policy Framework

Any host can put any domain name in the identifiers of a mail message, not only the name of the domain where it is located.

Two drawbacks of that freedom: it is a major obstacle to reducing unsolicited bulk email (UBE), or spam, because mail cannot be filtered by known UBE sources; and ADMDs worry about how easily others can use their domain names, often maliciously.

Sender Policy Framework (SPF) (RFC 7208) — the standardized way for a sending domain to identify and assert the mail senders for that domain. Compliant ADMDs publish SPF records in the DNS listing the hosts permitted to use their names in the “MAIL FROM” or “HELO” identities; compliant receivers use them to test the authorization of a sending MTA during the mail transaction.

SPF checks the sender’s IP address against the policy at the sending domain: the domain used in the SMTP connection, not the domain in the message header shown by the MUA. So SPF can be checked before the message content is received.

19.9DomainKeys Identified Mail

SPF authorizes a sending host; DKIM lets a domain cryptographically sign the message itself.

DomainKeys Identified Mail (DKIM) (RFC 6376) — a specification for cryptographically signing email so that a signing domain can claim responsibility for a message in the mail stream. Recipients verify by querying the signer’s domain directly for the public key, confirming the message was attested by a holder of the domain’s private key. Widely adopted by corporations, government agencies, gmail, Yahoo! and many ISPs.

Email threats (RFC 4686)

RFC 4686 describes the threats DKIM addresses by the attackers’ characteristics, capabilities and location.

Threat levelAttackers
LowWant to send email the recipient does not want, using commercially available tools to falsify the origin address, so spam cannot be filtered by originating address or domain.
MiddleProfessional bulk spammers, often commercial enterprises sending for third parties, with MTAs, registered domains and networks of compromised computers (zombies) to send messages and harvest addresses.
HighThe most sophisticated, financially motivated senders (e.g., email-based fraud). All of the above, plus attacks on Internet infrastructure itself: DNS cache poisoning and IP routing attacks.
Capabilities an attacker might have (11)
  1. Submit messages to MTAs and MSAs at multiple Internet locations.
  2. Construct arbitrary header fields, including ones claiming to be mailing lists, resenders and other agents.
  3. Sign messages on behalf of domains under their control.
  4. Generate many unsigned or apparently signed messages for a denial-of-service attempt.
  5. Resend messages previously signed by the domain.
  6. Transmit messages with any envelope information.
  7. Act as an authorized submitter from a compromised computer.
  8. Manipulate IP routing: submit from specific or hard-to-trace addresses, or divert messages to a domain.
  9. Limited influence over parts of DNS (e.g., cache poisoning), to influence routing or falsify DNS-based keys or signing practices.
  10. Significant computing resources (worm-infected zombies) for brute-force attacks.
  11. Eavesdrop on existing traffic, perhaps from a wireless network.

Location. DKIM focuses on attackers outside the administrative units of the claimed originator and the recipient. Inside them, other mechanisms such as authenticated message submission are easier to deploy; outside, the trust relationships those need do not exist and do not scale. External attackers exploit the “any-to-any” nature of email that makes recipient MTAs accept mail from anywhere: unsigned messages, incorrect signatures, correct signatures from barely traceable domains, or posing as mailing lists, greeting cards and other agents that send on behalf of others.

DKIM strategy

DKIM is transparent to the end user. The message is signed with the private key of the administrative domain it originates from; the signature covers all the content and some RFC 5322 headers. At the receiving end the MDA gets the public key through DNS and verifies, so mail claiming a domain it did not come from fails and can be rejected. S/MIME and PGP instead sign with the originator’s private key. Reasons for DKIM:

  1. S/MIME needs both sender and receiver to use it; most mail sent and received does not.
  2. S/MIME signs only the content, so RFC 5322 header information about origin can be compromised.
  3. DKIM is not implemented in MUAs, so the user need not do anything.
  4. DKIM applies to all mail from cooperating domains.
  5. Good senders can prove they sent a message, and forgers cannot masquerade as them.
Figure · DKIM deployment and functional flowFigures 19.10–19.11
  • Signing is done by an authorized module in the signing ADMD (MUA, MSA or MTA), using private information from a key store. The default algorithm is RSA with SHA-256; RSA with SHA-1 may be used.
  • Verifying is done in the verifying ADMD (MTA, MDA or MUA) using public information from the key store, retrieved through DNS. The flow may cross other ADMDs on the handling path.

The DKIM-Signature header

The signature is inserted as an additional RFC 5322 header starting with Dkim-Signature. Each field is a tag code, “=”, the value, and a semicolon.

19.10Domain-Based Message Authentication, Reporting, and Conformance

SPF and DKIM let senders advise receivers through DNS, but neither tells a receiver whether they are in use, and neither tells the sender how well they work.

DMARC (RFC 7489) — lets email senders specify a policy for how their mail should be handled, the types of reports receivers can send back, and how often. It works with SPF and DKIM, standardizing how receivers perform email authentication with them.

Example of the gap: a message arrives with no DKIM signature. DKIM alone cannot tell the receiver whether the message is authentic from a sender that does not use DKIM, or a spoof.

Identifier alignment

MechanismAuthenticates
DKIMThe domain that affixed a signature (d=).
SPFThe SMTP envelope (RFC 5321): the MAIL FROM domain, the HELO domain, or both. Usually not visible to the end user.
DMARCThe From domain in the message header (RFC 5322).

The RFC 5322 From field is DMARC’s central identity because it is a required header (always present) and most MUAs display it as the originator. End users identify the source by it, so it is a prime target for abuse. DMARC requires the From domain to match (be aligned with) an authenticated identifier: the DKIM signing domain, or the SPF-authenticated domain.

DMARC on the sender side

A DMARC sender must also use SPF, DKIM or both. It posts a policy in a DNS TXT RR as semicolon-separated tag=value pairs, and sets up addresses to receive aggregate and forensic reports. Those addresses are published unencrypted in DNS, so they invite UBE; the poster needs abuse countermeasures.

v= versionMust be first; always DMARC1.

Once the DMARC RR is posted, the sending side typically processes mail as follows:

  1. The domain owner publishes an SPF policy, configures DKIM signing, and publishes a DMARC message-handling policy.
  2. The author hands a message to the domain owner’s designated mail submission service.
  3. The submission service passes details to the DKIM signing module, which signs.
  4. The submission service relays the signed message to its transport service for routing.

DMARC reports

Aggregate reports

Sent periodically by receivers, with figures for successful and failed authentications: the sender’s policy for the interval; disposition (delivered, quarantined, rejected); SPF and DKIM results per identifier; whether identifiers aligned; results by sender subdomain; the sending/receiving domain pair; the policy applied and whether it differs from the one requested; the number of successful authentications; totals for all messages.

Forensic reports

Help refine SPF and DKIM and alert the sender that its domain is used in phishing/spam. Like aggregate reports, plus: as much of the message and header as reasonable, with an Identity-Alignment field; optional Delivery-Result; DKIM Domain, Identity and selector (and optionally canonical header and body); and an extra failure type for when mechanisms fail to give aligned identifiers.

SP 800-177 rolloutStart with p=none, so failing mail is handled by the receiver’s local policy. As aggregate reports show how well outside receivers authenticate your mail, move to p=reject. Receivers, from their own traffic analysis, decide whether a sender’s p=reject is trustworthy enough to act on.

Review Questions

Review questions 19.1–19.9 from the book. Answer first, then open to check.

19.1 What types of interoperability issues are involved in internet mail architecture and how are they handled?
  • User to user: the author’s MUA formats the message (RFC 5322, MIME) so the recipient’s MUA can display it.
  • MUA to MHS: when a message is posted (ESMTP/SUBMISSION from MUA to MSA) and when it is delivered (MDA to Message Store, then IMAP or POP to the recipient’s MUA).
  • Among MTAs along the transfer path: SMTP.
19.2 What are the SMTP and MIME standards?
  • SMTP (RFC 821, now RFC 5321): the protocol that encapsulates a message in an envelope and relays it from source to destination through MTAs, by text commands and replies over TCP.
  • MIME (RFCs 2045–2049): an extension to the RFC 5322 message format that adds five header fields, standardized content types and transfer encodings, to overcome SMTP/5322 limits such as 7-bit ASCII only and no binary objects.
19.3 What is the difference between a MIME content type and a MIME transfer encoding?

The content type (Content-Type, type/subtype) describes what the data in the body are, so the receiving agent can choose how to present them. The transfer encoding (Content-Transfer-Encoding) describes the transformation applied to represent the body in a form acceptable for mail transport, e.g., base64 or quoted-printable.

19.4 Briefly explain base64 encoding.

The input is taken three octets (24 bits) at a time and split into four 6-bit groups; each 6-bit value selects one of 64 printable ASCII characters. So every 3 octets of binary become 4 characters, which pass through mail transport programs unchanged. The input is converted blindly, whatever its content.

19.5 Why is base64 conversion useful for an email application?

Signing and encryption produce arbitrary 8-bit binary octets, but many mail systems accept only ASCII text. Base64 turns the binary into printable ASCII that mail-transport programs will not alter, so encrypted or signed messages arrive intact.

19.6 What is S/MIME?

Secure/Multipurpose Internet Mail Extension: a security enhancement to the MIME email format standard, based on RSA Data Security technology, providing digital signatures, encryption, compression and email-compatible encoding for MIME entities.

19.7 What are the four principal services provided by S/MIME?
  • Authentication: digital signature, typically RSA with SHA-256.
  • Confidentiality: message encryption, typically AES-128/CBC with a one-time key sent under RSA.
  • Compression.
  • Email compatibility: radix-64 (base64) conversion to ASCII.
19.8 What is the utility of a detached signature?
  • A user can keep a separate log of signatures of all messages sent or received.
  • A detached signature of an executable program can detect later virus infection.
  • When several parties must sign a document, such as a legal contract, each signature is independent and applies only to the document; otherwise signatures would have to be nested.
19.9 What is DKIM?

DomainKeys Identified Mail (RFC 6376): a specification for cryptographically signing email with a private key of the originating administrative domain, so the domain claims responsibility for the message. Recipients retrieve the public key from the signer’s domain through DNS and verify. It is transparent to users, covers the body and selected RFC 5322 headers, and applies to all mail from cooperating domains.
